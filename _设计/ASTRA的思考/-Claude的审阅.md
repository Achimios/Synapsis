## 2. 我在代码里核实到的三处缝隙（实测）

ASTRA 看不到代码，这三处是我拿它的论点去对代码时发现的。

### 2.1 证据等级的四个值混了两个维度（ASTRA A6 说对了）
- 现状：`evidence=实测|设计|估计|未验`，一个字段四选一（`app/src/shell.jsx:36,144,994`，手册第 7 条）。
- 问题：**「设计」说的是「应该怎样」（主张类型），「实测 / 估计 / 未验」说的是「观察到怎样、有多可信」（证据）。** 一个节点完全可以既是设计要求、又已实测。现在只能二选一。
- 代价很低：frontmatter 本来就能放任意键，不需要迁移、不需要改 schema。
- **建议（待拍板）**：先不加字段。在 `Philosophy.md` §3 记一句「设计 ≠ 证据等级，是两个轴；等真遇到摩擦再拆」。

### 2.2 FK（读回）其实只做了一半
- `Philosophy.md` §1 写的是：状态 **「从项目读回（不是手填）」**。
- 实测：`status` 是手填的 meta（CLI `status <id> done` 或界面右键）。`check` 只验证 `code:` 指向的文件和符号**存不存在**，不读回任何「现在怎样」。
- 这正是 ASTRA 的成本账本里 **C维护** 那一项：图不会自己跟着项目更新，就会慢慢烂掉。
- **这是哲学文档和实现之间最大的落差**，比任何新提案都重要。

### 2.3 证据会过期，但现在没人管（ASTRA H3，最容易落地的一条）
- 现状：节点标了 `evidence=实测` 之后，就算 `code:` 指向的文件后来改得面目全非，这个「实测」也永远是绿的。
- 这就是 Philosophy §3.2 的那句「**草稿不会悄悄变成谎言**」——只是在时间轴上又多了一种说谎方式。
- 可能的最小做法（**推测，没验证**）：标实测时顺便记一下 `code` 文件的 git 提交号或内容 hash；`check` 发现文件后来变了，就给一条 info：「实测之后代码改过，结论可能要重验」。纯 Node 能测，符合本项目「能在 Node 跑就放纯函数」的规矩。
- 只提示、不自动作废，正好符合 ASTRA 自己写的反面条件：既不能「旧结果永远有效」，也不能「一改全作废」。

### 2.4 顺带：check 和「形式化逐节点」有一点冲突
- `Philosophy.md` §4 说「check 只对升到该级的节点生效」，ASTRA B4 说「有些草稿可以永远是草稿」。
- 实测：`checkWorkspace` 对**每一个**没 status 的叶子都报 warn（`core/workspace.js:435`）。一张随手记的草稿图会一片黄。
- 这是个小事，但方向上它在逼人提前形式化，正是 Shipman & Marshall 警告的那种。值得记进摩擦观察，看你用的时候烦不烦。

### 7.2 你自己的话里，有三句比 ASTRA 的提案更像 Synapsis 的地基
1. **「解方程的意义在于计算过程中尽量保持无损的中间态」**（《解方程》）。这就是 Synapsis 在做的事：把思考的中间态外置，不让它在脑子里有损地糊掉。比「思维草稿工具」更准的一句定位。
2. **「测量域覆盖运行域，理论可以大量黑盒」**（《1.0》）。旧 Claude 补了三个失效条件：长尾、跨过非线性临界点、对抗。**这正好是证据「适用范围」该叫的名字**：一条实测证据的测量域是哪个版本、哪些场景；运行到域外就不担保。已经写进 `Philosophy.md` §3 的注脚，用的是你的词，不是 ASTRA 的「适用范围」。
3. **「外部群」**（《理解和推理》）。群论证明不成立，但直觉是对的：**反馈必须来自系统外、和真实目标挂钩**。放到 Synapsis 上：图本身是「内部」，从项目读回的状态（FK）才是「外部群」。所以 §2.2 说的「FK 只做了一半」，用你自己的框架看也是最该补的。

### 7.3 能直接用在 Synapsis 的两个想法（都是想法池，没排期）
- **教学顺序 = 形式化顺序**（旧 Claude 讲拉普拉斯时说的）：先看行为，再看极点图，最后才是符号。Synapsis 的「便签 → 类型 → spec → code → 实测」是同一个方向。以后写手册 / 引导，也按「先行为后定义」写。
- **跨层词汇表**：同一个概念在数学层 / 理论层 / 工程层各对应什么。这在 Synapsis 里可以是「一个节点 + 三条跨层边」，或者一条标签轴。等你规划 CFD 项目时可能真用得上，现在不做。
