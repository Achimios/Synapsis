# Synapsis · 哲学与定位

> 2026-10-07 与用户讨论整理。👤 = 用户原话或用户拍板。

## 1. 一句话
**Obsidian 的图是笔记链接的副产物，回答「我知道什么」；Synapsis 的图是设计出来的结构，回答「我在造什么、造到哪了」。**

| | Obsidian 图谱 | Synapsis |
|---|---|---|
| 单位 | 一篇篇文本，全局 | 一个项目内部的结构：脑区 → 区块内部 → 神经元/空间 |
| 位置 | 力导向，无意义 | 人摆的，有意义 |
| 边 | 链接，无类型无方向 | 有类型、有方向、带证据等级（估计/实测） |
| 状态 | 无 | ✅◐○，**从项目读回**（不是手填） |
| 层级 | 平 | 一等公民，可钻进去 |
| 绑定 | 一堆笔记 | 一个工作空间（被规划的项目） |

## 2. 软件运动学（👤用户的框架，见 `E:\z_from_oldLaptop\ObsidianVaults_V3\-人类思维笔记\L_AkiDynamic\3-1*`）
- 动力学 = 代码本身（LLM 时代已不是瓶颈）
- **运动学 / 显现层 = Synapsis 画出的结构**
- 意图路由 = 草稿节点写意图 → 导出给 LLM → LLM 建执行链
- 闭环：**IK 顶→底**（人画意图 → LLM 改代码）；**FK 底→顶**（读回 `_开发进度` / `_开发索引` / check 结果 → 节点变色）

👤「瓶颈不再是代码本身和技术困难，而是对架构的掌控、对项目结构的了解、对代码关系的可见。尽量降低专用技巧的入门成本，中间由 LLM 桥接，人类意图的传达和对关系的可见最重要。」

## 3. 三件真正新的东西
1. **每条主张带证据等级**（【实测】【设计】【估计】【未验】成为数据结构）
2. **草稿能被 lint**：节点标 ✅ 但 code 指向不存在 → 报错，草稿不会悄悄变成谎言
3. **LLM 是一等读者/作者**：渐进披露导出 + CLI 查询 + 补丁式修改

## 4. 形式化是逐节点的，不是全工具的
`便签 → 有类型 → 有 spec → 有 code 链接 → 有实测`。check 只对升到该级的节点生效。
（参考：Shipman & Marshall 1999 *Formality Considered Harmful* —— 过早要求结构，人会停止思考或乱填。）

## 5. 思维路径的证据（不是猜）
`Life Games/研究/用户笔记_AI空间.md` 的写法：**先甩一串清单（`/` 分隔）→ 再补关系 → 再加横切原则**。没有一步是「拖一个方框」。
→ 第一版：**打字优先，摆放其次**（大纲式输入，节点出现在画布，之后再拖）。

## 6. 范围（👤）
- 先只做游戏 AI 行为规划这一个案例；通用性只留在数据模型里。「建罗马和巴黎，不建迈阿密」——路（数据模型）先铺好，功能跟着案例长，长堵了就安排一次奥斯曼式重构。
- 主要给**人类自己思考草稿**用；方便编辑；可输出结构化文本指挥 LLM。
- 将来用于游戏设计规划，层级会非常多；AI 行为只是视图里一小块。

## 7. 首轮讨论定下的东西（2026-10-07，防止压缩后丢失）
> 原始对话在 Claude Code 的会话记录里；这里是结论。👤 = 用户定的。

**7.1 「超越 Notion」到底超越在哪**（Claude 首轮的判断，用户认可）
画布、拖拽、折叠只是壳（库都做得很好）。真正新的是 §3 那三件：**证据等级成为数据结构**、**草稿能被 lint**、**LLM 是一等读者/作者**。三者合起来才是「下一代思维草稿 / PLAN / PRD 工具」。

**7.2 思考与规格是相反的**
思考要低摩擦、允许模糊；规格要类型、校验、证据。解法 = §4「形式化是逐节点的」：凌晨三点随手记的便签和接上 `code` 的决策节点可以在同一张图里。Notion 要你先建数据库再填内容；Synapsis 是先有内容、结构慢慢长出来。

**7.3 存储：一节点一 .md（而不是一图一 JSON）**——理由：人能直接读写、LLM 原生（文件本身就是节点卡）、按节点 git diff 冲突少、一个节点可出现在多张图、直接兼容 Obsidian；坐标单独放 `_layout.json`。已实现（`core/workspace.js`）。

**7.4 👤 用户回答的四个问题**
1. 主要读者：**人类自己思考草稿**；要方便编辑；可输出结构化文本给 LLM、指挥它。
2. 范围：**先不通用**——只做游戏 AI 行为这一个案例；以后用于游戏设计规划，层级会非常多，AI 行为只是视图里一小块。
3. 「建罗马和巴黎，不建迈阿密」：一个案例上的成熟进步带来整体的结构探索（发散式推进）。七丘 = 游戏NPC状态空间组（罗马的发源地）。
4. 和玩法比的优先级：用户没给数字；Synapsis 由用户和 Claude 一起维护，用户累时文字丢在对话里，Claude 代记。

**7.5 检验方式**
- **自举**：用 Synapsis 写 Synapsis 自己（`__synapsis/Synapsis/`，`check` 0 错）——写得顺说明通用，卡住的地方就是下一步。
- **需求来源 = 摩擦日志**（`-给人类的解释/-摩擦日志.md`），不是功能清单。

**7.6 风险提醒（基石原话的延伸）**
这是「造工具的工具」，最容易陷进去。「别把地基当成目的」——判断标准：今天的改动有没有让用户**更快地想清楚一件游戏设计的事**。

**7.7 后来定下的（详见各文件）**
- 画布 = React Flow（`Decision_Canvas.md`）；导航是主功能、中键 = 基变换、嵌入衡量「同类」不是「相连」（`Navigation.md` §2–§3.6）
- 托盘程序 = Electron（Node + Chromium，Obsidian 同款），不需要 Python

**7.8 矩阵、决策树等「富内容」放哪（2026-10-07，👤 问要不要自定义后缀）**
- **不发明新后缀。** 自定义后缀 = Obsidian、GitHub、编辑器、LLM、grep 全都不认识它；`.md` 是所有工具的公约数。
- **决策树 / 状态机本来就是图** → 就是子节点 + 边，Synapsis 已经会画（「免费」）；要的只是换个布局（树形 / 状态机）。
- **小矩阵、表、公式** → 节点正文里的围栏代码块：```matrix（CSV 式行）、```mermaid、```math。没装 Synapsis 的地方照样能读（显示为代码），LLM 原生能读，Synapsis 识别语言名后在卡片里渲染成热力图 / 表。
- **大数据**（权重矩阵、采样、潜空间点云）→ 节点旁标准格式文件（`.csv` / `.json` / `.npy`），和图片一样放 `_pics_` 式的旁挂文件夹或 frontmatter 指过去（`data: _data_名字/W1.csv`）。
- 判据：**格式要让「没有 Synapsis 的人和 LLM」也能读**；Synapsis 只负责把它画得好看。

>

### 8.1 一个补充定位，而不是替换原定位

**让人可以构造、改变和检验表征；让意图、实现与反馈能够在同一个可操作空间里互相追踪。**

“在自己脑海里导航”保留为体验目标；工程上可直接观察的是用户留下的草稿、关系、选择、操作轨迹，以及接入项目后的反馈，不把这些自动等同于对真实神经活动的测量。

本节把“严肃的认知工程工具”理解为能追踪约束与证据，把“有生命感的外置大脑”理解为允许模糊、试探、重组和反悔。二者可以共存，不要求所有思想立即成为规格。

来源：原 §2、§4、§6；`Navigation.md` §0、§3；用户本对话观点。以上定位措辞为 ChatGPT 新提案。

### 8.2 关于“计算、表征、映射”的严谨边界

保留用户“人脑／机器其实不会计算”的原始命题，另提出一个可讨论的操作性版本：**不把计算当成独立于实现的神秘能力，而研究什么结构、状态、表征和局部操作实现了它。**

这不是证明“人脑只会查表”“MLP 只是乘法表”或“智力等于免计算”。本轮不把这些强命题升级成科学结论。

可以用一个成本账本评价表征是否有用（分析框架，不是实测定律）：

\[
C_{\mathrm{总}}=C_{\mathrm{构造表征}}+C_{\mathrm{转换}}+C_{\mathrm{求解}}+C_{\mathrm{验证}}+C_{\mathrm{维护}}
\]

关注整个闭环，而不只关注生成代码或切换布局那一瞬间是否更快。

“减少专用工具操作的记忆负担”与“专门知识不再有价值”需要分开讨论。意图、约束、异常识别和结果判断仍应在系统中有明确承担者。本段是对用户原命题的收窄提案，不冒充用户改口。

### 8.3 “基变换”保留为产品语言，底层区分三种操作

| 操作 | 意义 | 建议边界 |
|---|---|---|
| 线性换基 | 同一向量在不同基下的坐标表达 | 只有满足对应数学条件时才作严格换基解释 |
| 投影／视图切换／布局插值 | 同一批对象换一种呈现方式 | 不承诺无损；动画中间态不自动具有语义 |
| 重表征／重新建模 | 改变对象、关系或问题分解 | 是模型变更，应留历史与映射，不伪装成无害的视角切换 |

设计布局仍是用户摆放的布局。建议将观察层的临时布局与用户确认的语义编辑分开处理；不得因切换语义视图自动覆盖人的设计位置。

来源：`Navigation.md` §2、§3。三分法及相应边界为新增提案；滑杆、设计布局、只提示不改图是原文件已有想法或原则。

### 8.4 思维图、可执行图与 MLP：允许贯通，不强行等同

可保留“同一张图从草稿长成网络”的方向，同时区分：概念草稿、明确输入输出的可执行子图、具有明确数值规则的神经网络，以及由 FK 读回的运行观测。

**同一工作空间可以承载它们及其可追踪对应；不是所有节点都必须成为神经元，也不是有权重的关联图自动就是 MLP。** 概念节点与代码模块、数值单元之间可能是一对多或多对一；本轮不假定已经存在相应实现。

建议对边逐步说明“相似、属于、依赖、变换、假设因果、观测”等语义，但不向未形式化草稿强制加类型。

关联扩散的亮度、真实运行值、主张可信度、证据充分程度应分开。人接受了一个建议，只能表示授权纳入图中，不自动表示该关系已经实测成立。

来源：原 §3–§4；`Research_Landscape.md` §3③；`Navigation.md` §3.6。

### 8.5 软件运动学：带约束的反求与两个闭环

保留原文 IK（意图 → 实现）与 FK（项目状态 → 图）的定义，在此之上探索：

**外环：意图澄清。** 比较不同解释、场景与取舍，帮助人确定目标；改目标必须显式。

**内环：实现求解。** 在已确认目标和硬约束下寻找实现，再通过 FK 收集反馈。失败时不能悄悄降低目标或撤掉约束。

一个候选形式化描述为：

\[
\min_{x\in K}\left[D(F(x;S),I)+\lambda C_{\mathrm{改动}}(x,x_0)\right]
\]

其中，\(x\) 是实现，\(x_0\) 是当前实现，\(S\) 是评估场景集合，\(F\) 是这些场景下的可观察行为，\(I\) 是目标，\(K\) 是硬约束。它只是任务描述：不假定目标已经可量化、所有约束都可自动判断、整个软件连续可微，或可以求得全局最优。

反求可能有多解、无解或证据不足。建议让系统显露候选、代价、被固定的量与待人决定的自由度，而不是只给一个看似确定的修改结果。

### 8.6 形式化、主张类型、证据和适用范围：分开记录

原来的“便签 → 类型 → spec → code → 实测”可以继续作为工作过程；不把它解释成单一可信度分数。

| 维度（提案） | 问的问题 |
|---|---|
| 主张类型 | 这是设计要求、事实陈述、解释假设，还是建议？ |
| 形式化程度 | 只是草稿，还是已经有类型、规格和实现绑定？ |
| 证据 | 有什么观察或检查支持它？证据来自哪里？ |
| 适用范围 | 证据对应哪个版本、场景、输入和条件？哪些仍未知？ |

示例（构造例，不是项目现状）：“设计要求：受惊时仍保留任务承诺；已有实现；三种回放通过；夜间场景未测。”它不能仅被压缩成一个无条件有效的绿勾。

原有【实测】【设计】【估计】【未验】不在本轮自动迁移为新 schema；更不向所有便签强制增加字段。先在一个真实案例上手工记录，观察是否确实避免误解。

### 8.7 形式化也应该允许“解冻”

一个接上代码的“勇敢度”节点，仍可因解释力不足，退回多个候选分解：风险判断、任务价值、同伴承诺等。这里是构造例，不是发现了现有 NPC 的问题。

建议保留旧模型及其证据的历史适用范围；新模型不自动继承旧测试的保证。一个草稿也可以永远停留在草稿，不因为无法形式化而被判为失败。

### 8.8 发散灵感与检验边界

待探索方向：把比较、展开前提、暂停假设、重新分解做成可操作的“思考动作”；通过局部干预探索参数—行为敏感性；由 AI 提出能区分竞争解释的实验，而非只生成更多关联。

以上均是想法池条目，不是 v1 排期。最小实验候选见增补文档 H1–H3；沿用原 §7.6 的成功标准：是否更快、更可靠地想清楚一件真实游戏设计问题。

### 8.9 与现有设计的衔接提醒

`Navigation.md` §2 明确把中键换视角列为“等更多灵感再定”；原 §7.7 的压缩表述不应被据此解读为已经实现或最终定案。`Decision_Canvas.md` 明确选择 React Flow，但其记录仍注明用户手感比较与大规模性能未验证。本节不重新开放画布选型，也不替代这些验证。
